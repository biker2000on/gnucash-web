## Executive summary

The codebase is, in engineering terms, unusually clean for its size and its
AI-assisted history: zero `as any`, zero `@ts-ignore`, 3,880 passing tests with
2.68 assertions each, no self-mocking test files, and several genuinely
exemplary modules (`lot-scrub.ts`, `equity-comp-core.ts`, `compliance.ts`).

The problems are not sloppiness. They are **three specific classes of gap**:

1. **Authorization was retrofitted onto a single-tenant design.** Multi-book RBAC
   guards the routes it was applied to; the surfaces predating it (business
   entities, bearer-token scope) and one bootstrap path (`/api/auth/register`)
   are wide open.
2. **A core numeric primitive is wrong, and the app feeds it bad input.**
   `toDecimal()` only decodes power-of-ten denominators, while
   `impliedPriceFraction()` deliberately writes GCD-reduced fractions.
3. **Correct concurrency patterns exist but were applied per-site, not
   systemically.** The `74fc9a3` wave produced good patterns; code written after
   it re-implements the same operations without them.

**Ship-blocking:** items S1, S2, S3 below. S1 in particular should be treated as
an active incident if this instance is reachable from any untrusted network.

## CRITICAL — Security

### S1. Open registration grants `edit` on every book **[verified]**

`src/app/api/auth/register/route.ts:30-37`

`/api/auth/register` is exempted from the session gate (`src/middleware.ts:20`).
It has no invite code, no env flag, and no first-user-only check — verified by
grepping for `ALLOW_REGISTRATION` / `DISABLE_REGISTRATION` / `SIGNUP` (no hits)
and by reading `registerUser` (`src/lib/auth.ts:96`), which gates nothing. On
success it runs:

```ts
const books = await prisma.$queryRaw`SELECT guid FROM books`;
for (const book of books) {
    await grantRole(user.id, book.guid, 'edit', user.id);
}
```

**Exploit:** an unauthenticated stranger POSTs
`{"username":"x","password":"12345678"}` and immediately holds `edit` on every
book — all balances, transactions, payslips, statements, and documents for every
tenant. The login page ships a "Create Account" toggle that calls it
(`src/components/LoginForm.tsx:53`), so it is an advertised feature, not an
obscure endpoint.

The app already has a proper invite system (`/invite/[code]`, the invite flow in
`settings/users`). This endpoint bypasses it and grants strictly more.

**Fix:** gate behind an env flag defaulting to off, or require a valid invite.
Grant **zero** book roles on registration.

Related: OIDC first login auto-grants `readonly` on every book
(`src/app/api/auth/oidc/callback/route.ts:302-307`) — same bootstrap-by-granting-
everything pattern, lower severity.

### S2. Hardcoded session secret, committed to a public repo **[verified]**

`src/lib/session-config.ts:15`

```ts
password: process.env.SESSION_SECRET || 'complex_password_at_least_32_characters_long_12345',
```

The repository is **public** (`gh repo view` → `"visibility":"PUBLIC"`). Anyone
can seal an iron-session payload `{userId:1,isLoggedIn:true}` with that constant
and be admin.

The same constant derives the SimpleFIN credential key
(`src/lib/services/simplefin.service.ts:25,38`), so stored **bank access tokens**
are decryptable offline by anyone with a database copy or a backup. AI API keys
and TOTP seeds use `sha256(SESSION_SECRET || NEXTAUTH_SECRET || '')`
(`src/lib/ai-config.ts:10`, `src/lib/totp-store.ts:32`) — with both unset that is
`sha256("")`, plus AES-256-**CBC** with no authentication tag.

`src/lib/secure-config.ts:7` gets this right: it **throws** when the secret is
absent and uses AES-GCM. The four call sites above do not.

**Action:** verify `SESSION_SECRET` is set on the deployment. Then remove the
fallback (fail fast at startup), rotate the secret, and re-encrypt SimpleFIN,
AI-config, and TOTP rows.

### S3. AI-generated SQL can read any table, including password hashes **[verified]**

`src/lib/ai-query/guardrails.ts:36`, executed at `src/lib/ai-query/execute.ts:45`

`SCOPED_TABLES = ['accounts','splits','transactions','account_hierarchy']` is the
entire scoping rule, and there is no table allowlist. Probe run against the real
validator:

```
ALLOWED | SELECT username, password_hash FROM gnucash_web_users LIMIT 200
ALLOWED | SELECT api_key_encrypted FROM gnucash_web_ai_config LIMIT 200
ALLOWED | SELECT token_hash, user_id FROM gnucash_web_api_tokens LIMIT 200
ALLOWED | SELECT guid, root_account_guid FROM books LIMIT 200
ALLOWED | SELECT a.name, a.guid FROM accounts a WHERE $1 IS NOT NULL LIMIT 200
```

Two distinct defects:

- **No allowlist.** Every `gnucash_web_*` table is readable by any user with
  `readonly` on any book (`src/app/api/ai/query/route.ts:56`), and raw rows are
  returned to the caller.
- **The book-scope check only tests for the *presence* of the string `$1`.** The
  last line above satisfies it with an always-true predicate while returning
  every book's accounts. (Credit where due: `maskStringLiterals` correctly
  prevents a `$1` inside a string literal from satisfying the check.)

`READ ONLY` + statement timeout prevent writes but do nothing against
exfiltration.

**Fix:** replace the deny-list with an allowlist of readable relations (the
GnuCash financial tables only) and reject any identifier outside it. Require the
scope parameter to appear in a binding position, not merely anywhere in the text.

Two lesser defects in the same module: `castScopeParameter`
(`src/lib/ai-query/execute.ts:25`) rewrites `$1` **inside string literals**
(`'%$1%'` → `'%$1::text[]%'`) because it runs on raw rather than masked SQL; and
a `LIMIT` that appears only inside a CTE suppresses outer-`LIMIT` injection, so
`WITH t AS (... LIMIT 100) SELECT * FROM t CROSS JOIN splits` is unbounded.

## CRITICAL — Accounting correctness

### A1. `toDecimal()` misdecodes non-power-of-ten denominators — 718 real price rows are wrong **[verified against `gnucash_dev`]**

`src/lib/gnucash.ts:41` (dead duplicate at `src/lib/db.ts:127`)

```ts
let fractionStr = remainder.toString();
const precision = d.toString().length - 1;   // assumes d is a power of 10
fractionStr = fractionStr.padStart(precision, '0');
```

The decimal is reconstructed by *string padding* against the denominator's digit
count, which is valid only for `d ∈ {1,10,100,…}`.

**This is not theoretical, and it is self-inflicting.**
`impliedPriceFraction()` (`src/lib/services/implied-price.service.ts:57-63`)
divides numerator and denominator by their GCD and
`recordImpliedPrices()` stores the reduced fraction — so every investment
transaction can add another mis-rendering price row.

Read-only survey of the `gnucash_dev` database (exact power-of-ten test,
regex `^10*$`):

| table | total rows | non-power-of-10 |
|---|---|---|
| `splits.value_denom` | 50,628 | **0** |
| `splits.quantity_denom` | 50,628 | **0** |
| `prices.value_denom` | 72,705 | **718 (1.0%)** |

Real stored rows, with what `toDecimal` actually returns:

| stored fraction | true value | `toDecimal` | overstated |
|---|---|---|---|
| `8727032/58502535` | 0.14917357 | `0.8727032` | **5.85×** |
| `5227906/41001943` | 0.12750386 | `0.5227906` | **4.10×** |
| `658852/34042883` | 0.01935359 | `0.0658852` | **3.40×** |
| `9451225/31094529` | 0.30395138 | `0.9451225` | **3.11×** |
| `51735299820/1410065408` | 36.69 | `36.972945132` | 1.01× |

Affected commodities are mostly historical FX rates (USD 399 rows, CNY 234, EUR
31) plus a handful of NYSE/CRYPTO/FUND quotes.

**Good news:** the ledger itself is clean — **zero** of 50,628 splits are
affected, so no booked money is currently wrong. The damage is confined to
valuation surfaces that decode prices: `currency.ts:178,199` (`findExchangeRate`),
`account-valuation.ts:69`, `account-current-value.ts:78`, `commodities.ts:73`,
`api/dashboard/net-worth/route.ts:262,290`, `time-machine.ts:130`,
`investment-benchmark.ts:409`.

The codebase already contains the correct idiom — `reports/utils.ts:9`,
`reports/fx-revaluation.ts:363`, and `validation.ts:137` all use plain
`Number(num)/Number(denom)` and are immune. Two implementations therefore
**disagree on identical input**.

`src/lib/__tests__/numeric.test.ts` tests only denominators 0, 1, 100, 1000,
10000 — the bug lies entirely outside the tested domain.

**Fix:** replace the padding with exact long division; delete the dead duplicate
in `db.ts`; add tests for `1/3`, `1/8`, `3/64`, `1/256`.

**Also fix `CLAUDE.md:93`**, which directs all future work to `toDecimal()` from
`db.ts` — a function with **zero importers**. The live one is in `gnucash.ts`.

### A2. Manual FX/price entry stores rates at the currency's SCU, zeroing sub-cent rates **[verified]**

`src/app/api/exchange-rates/route.ts:98` and `src/app/api/prices/route.ts:131`
both call `fromDecimal(value, currency.fraction)` — 100 for USD.

| pair | entered | stored | reads back |
|---|---|---|---|
| EUR→USD | 1.0857 | `109/100` | 1.09 |
| **KRW→USD** | 0.00072 | **`0/100`** | **0** |
| **CLP→USD** | 0.00104 | **`0/100`** | **0** |

A ₩10,000,000 holding values at **$0.00**, and `findExchangeRate` returns zero
for every conversion in that pair.

The codebase knows the answer: `src/lib/yahoo-price-service.ts:23-25` defines
`PRICE_DENOM = 100_000_000` with a comment that sub-cent assets otherwise *"round
to $0.00."* The automated sync path is correct; the two manual routes are not.

**Fix:** use `1e8` in both routes.

### A3. Trading-split generator drops zero-quantity commodities, unbalancing Return-of-Capital

`src/lib/trading-accounts.ts:75` deletes a commodity when its net *quantity* is
~0, discarding its non-zero *value*. A $500 Return of Capital
(`InvestmentTransactionForm.tsx:206-226` emits `quantity_num: 0`) produces splits
summing to **−$500.00**.

`processMultiCurrencySplits` runs **after** `validateTransaction`
(`src/app/api/transactions/route.ts:361`) and the result is never re-validated.
`investment-entry-regressions.test.ts:71-81` asserts the payload balances — which
it does, *before* trading splits are appended.

**Fix:** retain a commodity when quantity **or** value is non-negligible; assert
`Σ value === 0` after generation.

### A4. Ledger inline edit forces `quantity_denom = 100`, corrupting share counts

`src/components/AccountLedger.tsx:584-623` — `toNumDenom(s.amount)` always yields
denominator 100 and is assigned to both value and quantity; the PUT handler
recreates splits verbatim (`src/app/api/transactions/[guid]/route.ts:285-312`).

Editing a description on a 2-split stock buy viewed from the *cash* side turns
`100000/10000` (10.0000 shares) into `250000/100` (2,500 shares). Value stays
balanced, so nothing errors. At 1e8 crypto precision the position is destroyed.

**Fix:** carry original `quantity_num`/`quantity_denom` forward for any split
whose amount was not edited.

### A5. Scheduled-transaction execution writes splits with no balance validation

`src/lib/services/scheduled-tx-execute.ts:152-160` inserts splits via raw SQL with
no zero-sum check, rounding each split independently at `denom = 100`. A balanced
1e6-precision template (33.333333 / 33.333333 / 33.333334 / −100.00) writes a
**−$0.01 imbalance**. `scheduled-tx-create.ts:95-96,150` has the mirror defect.

By contrast `POST /api/transactions` and `PUT /api/transactions/[guid]` both call
`validateTransaction`, which does enforce the invariant
(`src/lib/validation.ts:94-104`). The scheduled path is a bypass, not a systemic
absence.

## CRITICAL — Reliability

### R1. A paycheck can be posted twice **[verified]**

`src/lib/services/payslip-post.service.ts:191`

The only duplicate guard, `findMatchingTransaction`, runs on the global client
**before** the `$transaction` opens at `:245`. Neither transaction re-checks
inside, and the route's `payslip.status === 'posted'` check
(`src/app/api/payslips/[id]/post/route.ts:29`) is a plain read with no claim —
`status` is written only after posting succeeds.

Two concurrent requests (a double-click, or a browser retry on a slow
AI-extraction POST) both pass the guard and both create a full payslip
transaction: gross pay, every withholding, the 401k deferral, and the net
deposit. That doubles income, withholding, and retirement contributions, which
then flow into contribution-limit tracking and the tax estimator. Nothing detects
it afterward.

**Fix:** claim first —
`UPDATE ... SET status='posting' WHERE id=$1 AND status<>'posted' RETURNING id`
— then move the dedup check inside the transaction. This exact pattern already
exists at `src/lib/business/invoice-engine.ts:1246-1259`.

  Five explicit `: any`, each an acknowledged Prisma-transaction-client seam.

## What is genuinely good

  as the negation of summed rounded debits, so balance holds by construction.
- `src/lib/compliance.ts` — a correct IRC §7503 due-date roller including
  nth-weekday holidays and DC Emancipation Day.
